# Work journal — 2026-06-21 12:15

## Qué se hizo

**PR [#120](https://github.com/fmarrabal/openmiura/pull/120) (`74161bc`) — trust anchors for `openmiura verify`.** Merged to `main`.

`--trust-anchor` (repeatable) on `openmiura verify` binds an evidence pack to a
*known* signer. The offline verifier already proved a pack was internally
consistent and signed by *whoever* held the embedded key — it stopped at
"untampered", not "authentic". A forged pack signed with an attacker's **own**
real Ed25519 key passed every consistency check. Trust anchors close that gap.

Behaviour:
- **No anchor (default):** authenticity-of-signer not checked — byte-identical
  to prior behaviour.
- **≥1 anchor:** a pack is `authoritative` only if the fingerprint of the key
  its signature *actually verified against* (`embedded_fingerprint`, not the
  self-reported `integrity.public_key` metadata) is one of the anchors. Forged
  pack signed with an unknown key → non-authoritative, exit `2`.
- Dev-seed packs stay non-authoritative even if their (public) key is anchored;
  `--allow-dev-seed` never rescues an untrusted real-key signer.

Anchor resolution: PEM public-key file (Ed25519 or EC; a bundle of concatenated
blocks anchors **every** key), a text file mixing hex fingerprints and PEM
blocks, or a bare 64-char hex fingerprint. Fails loudly (exit `3`) on a typo,
an empty value, or an unsupported key type (RSA/…). Case-insensitive on the CLI
**and** the public `verify_pack(trust_anchors=...)` API. The exposed
`public_key_fingerprint` is now the verified key's fingerprint, so a value
copied from the report is exactly what `--trust-anchor` compares.

Files: `openmiura/evidence_verify.py` (verify_pack param + trust verdict,
`_resolve_trust_anchors`, `_fingerprint_of_pem`, `_print_human`,
`verify_pack_cli`), `openmiura/cli.py` (`--trust-anchor`),
`tests/test_cli_verify_trust_anchors.py` (17 cases), `README.md`.

## Decisiones tomadas

- **Expose the verified fingerprint, not the self-reported one.** Removed a
  foot-gun: the report's `public_key_fingerprint` now equals what the trust
  check compares, so an auditor copying it as an anchor cannot pick a value the
  check ignores.
- **Fail loud, not "trust nobody".** An empty/typo'd/unsupported anchor is a
  usage error (exit 3) rather than a silent downgrade to non-authoritative.
- **`hex64` before `is_file`.** A well-formed bare fingerprint is unambiguous
  and is never shadowed by a same-named file in the CWD.

## Riesgos / lo que Curro debe saber

- This is **mapping/strategy**, not a conformance claim. A green
  `--trust-anchor` result proves the pack was signed by a key the operator
  declared trusted; it does not by itself establish the human identity behind
  that key (that's PKI/enrolment, out of scope here).
- Cross-verifier fingerprint note (out of scope, pre-existing): the in-process
  service verifier (`scheduler/_portfolio_a_mixin.py`) reports a **DER**
  fingerprint for Ed25519, while the standalone tool + pack metadata use the
  **raw** fingerprint. They agree per-tool today; only a future cross-check that
  compared the two would surface the mismatch.
