# Work journal — 2026-09-19 11:25

## Adversarial security audit: find bugs and fix them

Curro asked for an adversarial audit of the project — find errors and
correct them. Five independent reviewers attacked distinct surfaces
(evidence cryptography, audit hash chain, authorization/approval controls,
concurrency and resource safety, operator/CLI paths), each instructed to
report only defects it could demonstrate.

**~45 findings came back. I reproduced every one I acted on with my own
scripts before touching code** — I did not take a reviewer's word for any
fix. The full register, including what is still open and why, is in
[`adversarial_audit_2026-09-19.md`](adversarial_audit_2026-09-19.md).

### What was fixed (8 defects, all pinned by regression tests)

The fixed set is deliberately narrow: the defects that corrupt the audit
chain **during ordinary honest operation**, plus the two that let a pack
signed with a publicly-known key read as authoritative.

**Audit hash chain (`persistence/`)** — three of these broke the chain with
no attacker involved, which is worse than a missed tamper: `verify-chain`
would report `TAMPER DETECTED` forever on a database nobody touched.

- **A1 — concurrent writers shared a `chain_seq`.** `compute_chain_link`
  was an unsynchronised read-modify-write of the per-scope head on a SQLite
  connection shared across threads (`check_same_thread=False`, no lock
  anywhere in `core/` or `persistence/`). My repro: 8 parallel `log_event`
  calls produced `[1,2,3,4,5,5,6,7,7]`. The append-only triggers then make
  the duplicate unrepairable.
- **A2 — a failed INSERT left the head advanced.** The head was written
  *before* the caller's INSERT; a benign `NOT NULL` violation left
  `chain_seq` `[1,3]` and a permanent gap, committed by the next writer.
- **A6 — `log_decision_trace` computed `MAX(version)+1` outside any
  transaction**, colliding on the composite PK after the loser had already
  advanced the head (this is what triggers A2 in production).

  *Fix*: a `chain_write(conn)` context manager in `persistence/base.py`
  holding a per-connection `RLock` across link → INSERT → commit, and
  rolling back on any exception. `compute_chain_link` now raises if called
  outside one, so a future writer cannot reintroduce the bug by forgetting.
  All four call sites wrapped.

- **A3 — deleting every row of a scope verified clean.** The verifier built
  its scope set from surviving rows only, so an emptied scope was never
  visited while its head sat in `audit_chain_heads` contradicting it.
  Truncating a whole table reported `intact`, exit 0. *Fix*: heads join the
  scope set; an empty chain with a head present is tamper.
- **A4 — `events` hashed the pre-serialization payload** while the verifier
  could only rebuild it by re-parsing `payload_json`. `{2:'b', 10:'a'}`
  sorts numerically before the round trip and lexicographically after, so
  an untampered chain failed. *Fix*: serialize once, hash the round trip.
- **A5 — `decision_traces` filtered `chain_seq IS NOT NULL` inside the
  verifier's own query**, so a forged row with NULL chain columns did not
  appear in the report at all while the application returned it as genuine.
  *Fix*: drop the filter so it surfaces as `preexisting_count`.

**Offline verifier (`evidence_verify.py`)**

- **B1 — one space defeated the dev-seed guard.** The guard re-derives the
  public development key from `signer_key_id`, but used the raw field while
  the signature binds the stripped one. Padding it, plus deleting the two
  *unsigned* `dev_signing_key`/`signing_warning` fields, turned a pack
  signed with the publicly-known dev seed into `VERIFIED`, `authoritative`,
  exit 0 — collapsing the whole "re-derive rather than trust a flag"
  defence. The exception path also defaulted to "not a dev key"; it now
  fails closed (reachable via a lone surrogate in the field).
- **B2 — `--allow-dev-seed` overrode a non-matching `--trust-anchor`**,
  because `_exit_code_for` never consulted `trusted_signer`. A CI job
  pinning its operator key accepted a dev-seed pack.

### Tests

- `tests/unit/test_audit_hashchain_pr8_atomicity.py` — 8 tests: concurrent
  writers, concurrent decision-trace versions, failed-insert rollback,
  scope erasure, table truncation, serializer parity (both directions —
  the honest chain verifies *and* real tamper is still caught), unchained-row
  visibility.
- `tests/test_cli_verify_devseed_guard.py` — 4 tests: padded `signer_key_id`
  cannot launder a dev-seed pack, `--allow-dev-seed` does not override a
  failing anchor, and the legitimate flag+matching-anchor combination still
  works.

**Authorization (`application/`, `interfaces/broker/`)** — added after Curro
reviewed the register and said to go ahead with these two.

- **C1 — the broker approve route bypassed signature-grade approval
  entirely.** `POST /broker/admin/releases/{id}/approve` called the legacy
  single-approver path unconditionally: a release governed by a quorum was
  approved there by its own creator, 200, status `approved`, **zero**
  signature-grade votes recorded — while the HTTP admin route refuses the
  identical call with 403. *Fix*: the refusal is now a property of
  `ReleaseService.approve_release` (it raises when a quorum is configured),
  so the two non-HTTP callers and any future one fail closed rather than
  each route having to remember to dispatch; the broker route additionally
  dispatches to the strict path so it works rather than merely failing.
- **C2 (demonstrated half) — body-supplied scope was never validated.**
  `payload.get("tenant_id") or auth_ctx.get("tenant_id")` short-circuits the
  scope check, which only ever sees the header scope, so a workspace-bound
  principal refused a scope in the headers reached it via the body. *Fix*: a
  public `AuthService.enforce_requested_scope` and a `resolve_request_scope`
  broker helper, applied to the approve route. ~280 further occurrences now
  have a helper to adopt; that pass is mechanical but wide and is left for
  its own review.

### What is NOT fixed, and why

Deliberately left open (full detail in the register). Three groups:

1. **Schema changes** — A7 (a row INSERTed with NULL chain columns still
   passes; needs a genesis watermark) and A8 (`release_approvals` has no
   append-only trigger). CLAUDE.md §3.3: ask before a DB-schema change.
2. **Semantics decisions** — B3 (a fabricated chain of custody is accepted,
   including under `--strict`), B4 (RFC 3161 anchoring accepts any leaf of
   the anchored CA — no EKU, no validity check), B5 (an invalid timestamp
   never affects the exit code), B6 (extra ZIP entries ride along). Each
   changes what `verify` accepts, so it needs a call about existing packs
   plus a matching update to the paper §3.3 and the Part 11 mapping.
3. **Route-layer work** — C1 (**the broker approve route bypasses
   signature-grade approval entirely**: the creator approves their own
   release, 200, zero signature-grade votes) and C2 (**broker routes take
   tenant/workspace scope from the request body**, defeating the validated
   header scope; ~280 occurrences). These are the two highest-value items
   in the whole register and need their own PR.

### A flaky test found on the way, and cleared

The full suite failed 3 evaluation tests once, then a different one on the
next run. That non-determinism traces to `list_evaluation_runs` ordering by
`started_at DESC` with no tiebreaker while `time.time()` has ~15 ms
resolution on Windows — two runs in the same tick order arbitrarily, so
"which run is latest" flips.

I did **not** assume it was pre-existing: I checked out pristine
`origin/main` in a throwaway worktree and reproduced the same failures
there (2 in 3 runs) with none of this pass's changes applied. It is
recorded as E9 in the register and left unfixed here, since it belongs with
the other operator/CLI items rather than in a security pass.

### Risks for Curro to review

- The `chain_write` guard makes `compute_chain_link` raise outside a block.
  That is intentional (it is what stops the bug coming back), but any
  out-of-tree caller of `compute_chain_link` would now fail loudly.
- B1's fail-closed default means a pack whose `signer_key_id` cannot be
  encoded is reported non-authoritative rather than authoritative. Correct
  for a security guard, and the blast radius is malformed packs only.
- **C1 is a live authorization bypass.** If the broker is enabled in any
  deployment, that route should be considered untrusted until fixed.
