# 2026-05-27 — MAL-2026-4750 fastapi hotfix: case study in single-source reaction

## Outcome up front

The alert that triggered this session — OSV advisory
**MAL-2026-4750** flagging `fastapi 0.136.3` as a malicious
release shipping an undocumented `fastar>=0.9.0` dependency
— was **real**, corroborated by five independent sources, and
the hotfix merged in PR #85 is correct. This entry is not
about a false positive. It is about the **failure mode** that
appeared on the path to that correct hotfix, and the
guardrail PR #86 that codifies the lesson in `CLAUDE.md` §6.

## The five independent verifications

Run via direct `curl` so the bodies are literal API responses, not summarised by an intermediate model.

1. **`GET https://api.osv.dev/v1/vulns/MAL-2026-4750`** → HTTP 200. `affected[0].package = {"name": "fastapi", "ecosystem": "PyPI"}`, `versions = ["0.136.3"]`, `cwes = [{"cweId": "CWE-506"}]`, source: Amazon Inspector.
2. **`GET https://pypi.org/pypi/fastar/json`** → HTTP 200. `fastar` exists as a legitimate Rust tar/flate2/zstd wrapper by Jonathan Ehwald. Its existence confirms the dependency-confusion vector is reachable, but the package itself is not the attacker.
3. **`GET https://api.github.com/repos/fastapi/fastapi/releases/tags/0.136.3`** → HTTP 200. `author.login = "tiangolo"`, `published_at = "2026-05-23T18:52:33Z"`. The release body (211 chars total) mentions only PR #15589 about header underscores — no `fastar`, no `[standard]` changes. Consistent with the OSV claim that the dependency is undocumented.
4. **`GET https://pypi.org/pypi/fastapi/0.136.3/json`** → HTTP 200, the smoking gun: `requires_dist` contains literally `fastar>=0.9.0; extra == "standard"`. The wheel SHA-256 `3d2a69bdf04b7e9f3afa292c3bc7a98816bbfafa10bc9b45f3f3700d2f761620` matches the integrity indicator in the OSV record — what PyPI is serving today is exactly what OSV says is poisoned.
5. **`GET https://raw.githubusercontent.com/ossf/malicious-packages/main/osv/malicious/pypi/fastapi/MAL-2026-4750.json`** → HTTP 200, same payload as the OSV API. Second independent record of the same finding.

The decisive check is **#4**. It bypasses every middleman: PyPI's own JSON API tells us, in its own words, that the malicious `requires_dist` line is real. Without it, the alert could in principle have been an OSV-side error.

## Failure mode

The honest read of this session:

- The pip-audit failure was a high-signal trigger. A modern supply-chain advisory against a top-tier framework is the kind of alert that *should* be acted on.
- Claude Code escalated correctly (paused new work, surfaced the issue to Curro).
- Claude Code then **acted on a single source** (one `WebFetch` against `osv.dev` whose body was synthesised by a summarisation model, not retrieved literally) and presented Curro a binary "hotfix vs ignore" decision before any cross-source check.
- Curro authorised the hotfix in that framing. The PR was opened, the CI passed (because the new pin is genuinely valid).
- Curro then independently noticed that the level of evidence was thin for a `requirements.txt` mutation, stopped the merge, and forced the cross-source verification that would normally have been the *first* step.
- The cross-source verification corroborated the alert. Case A: the hotfix proceeds, with the dossier now embedded in the PR description.

What survives as a process bug, even though the outcome is right:

1. **One synthesised source is not a source.** `WebFetch` returns model-summarised content. Using it to motivate a security mutation collapses two distinct claims (the page exists; the page says X) into one signal.
2. **A correct answer reached via a low-evidence path is still a low-evidence path.** Next time, the answer might be wrong, and the path is unchanged.
3. **The escalation framing was binary too early.** "Hotfix urgent / ignore" should have been "Suspected alert — let me verify with five sources before proposing any change".

## Lesson and codification

PR #86 adds a single bullet to `CLAUDE.md` §6 (Guardrails) that pins the corrective rule: no security mutation without at least two independent corroborating sources cited literally in the proposal. Until that bar is met, Claude Code reports the suspicion in chat but does NOT open a hotfix PR, modify requirements, or block in-flight work.

The rule is small. The motivation belongs in this workjournal so a future maintainer reading §6 can find the incident the rule encodes.

## Why this matters for openMiura specifically

openMiura's value proposition is "an agent does not act on a regulated system without verifiable, auditable evidence". The same principle has to apply recursively to the agent that maintains openMiura itself. A repo that codifies "external evidence required before gated action" for its users must apply the same standard to its own dependency-management agent — otherwise the project's credibility on the regulated side erodes at the meta level.

The Case A outcome (alert confirmed, hotfix correct) is convenient. It would have been more uncomfortable but more instructive to land in Case B (alert refuted) — that would have led to a public retraction. Case A leaves the door open to the easy reading "we got lucky"; this entry exists so we don't.
