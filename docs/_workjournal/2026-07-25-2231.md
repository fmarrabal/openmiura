## End-to-end simulation of openMiura for the arXiv paper

Curro asked for a complete simulation of openMiura "in action", saving
images and results, to later write up the paper (there is already a
draft) for arXiv. This session builds a reproducible harness that runs
the **real** system and renders paper figures from the captured output —
nothing mocked, no outcome hand-authored.

### What was built (`docs/academic/simulation/`)

Three scripts, run in order:

1. **`run_simulation.py`** — drives the real FastAPI app over an
   in-process TestClient against a persistent SQLite DB, exercising four
   scenarios and writing JSON + a transcript:
   - **A. Governed runtime** (the project's canonical demo): a sensitive
     policy change is blocked at *pending_approval*, executes only after
     a distinct approver signs, leaves a signed release. 9/9 checks pass.
   - **B. NMR pilot** (`scripts/run_pilot_ual_nmr_demo.py`): nominal path
     requires `nmr_reviewer`; the unknown-impurity path escalates to
     `pi_approver`.
   - **C. Signature-grade approval**: creator self-approval, unknown
     identity and missing-TOTP are all rejected (403); two distinct
     TOTP-authenticated approvers reach the n-of-m quorum; each writes an
     Ed25519 signature on the audit hash chain.
   - **D. Evidence pack**: a real signed pack (81 KB) exported for
     offline verification.
2. **`verify_and_tamper.py`** — the auditor's side, capturing every exit
   code and verdict:
   - `db verify-chain` → all chains intact (exit 0).
   - `verify <pack>` → VERIFIED; with `--trust-anchor <real fpr>` →
     authoritative (0); with a foreign anchor → NON-AUTHORITATIVE (2); a
     one-byte edit to signed content → FAILED (1).
   - Two-layer tamper-evidence: a plain `UPDATE` on `events` is rejected
     by the append-only trigger; a direct edit to a signed row in the
     trigger-free `release_approvals` is caught by the hash chain
     (first_bad_seq pinned).
   - **RFC 3161**: a real trusted timestamp from freetsa.org over the
     pack signature, verified offline (genTime attested).
3. **`make_figures.py`** — renders seven figures (PNG + vector PDF) from
   `results/` only; no figure hard-codes an outcome.

Artifacts committed: the three scripts, `results/*.json` + transcripts,

### Honesty correction surfaced by the simulation

The run showed that the append-only DB **triggers exist only on**
`events`/`tool_calls`/`decision_traces` — **not** on `release_approvals`
(by design; confirmed in `migrations/_batch_003.py` `_TRIGGER_TABLES` and
`test_audit_hashchain_pr4_triggers`). `release_approvals` is protected by
the hash chain, not a trigger. My PR #158 text (paper §3.3 and the
Part 11 §11.10(e) mapping) had said "database triggers reject any
UPDATE/DELETE" over all four tables. Corrected both to the accurate
**two-layer** description (triggers on the three operational tables; the
chain covers all four, including the trigger-free approvals table). The
Medium draft carried the same imprecision and was tightened to match.
This is a better, more precise story — and it is exactly what the
simulation now demonstrates (Fig. 3).
